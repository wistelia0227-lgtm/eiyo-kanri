### 既存の nutrition-app との関係
既存の nutrition-app（献立カレンダー・料理マスタ・栄養価計算、localStorage）は献立側。こちらは利用者側で、責務が重ならない。
既存側の保存方式（localStorage、5〜10MB）は体重の時系列や変更履歴を溜めるのに足りないため、こちらは IndexedDB で新しく作った。
献立と成分表は後段でこちらに取り込み口を作る（成分表は `eiyo-kanri_research\data\foods.js` に、推定値・微量・未測定の区別を残した形で変換済み）。

## 2. 設計の核

- **枠** `{ d:'2026-09-20', m:'l' }` = いつの・どの食事か。在籍も欠食も食事変更も、全部「どの枠から」で持つ
- **在籍の判定は 1 つ**: 在籍期間 + 利用する曜日 + 食べる食事 + 欠食。入所・ショート・デイを別々に処理しない（デイは「月〜金の昼だけ」の人）
- **消さない**: 取り消しは `cancelledAt` を付けるだけ。在籍・欠食の変更は `changes` に前後の値が残る（締切後の変更の検出と、監査の証跡を兼ねる）
- **計算は `js/model.js` に集約**。DOM にも DB にも触れないので Node で試験できる

## 4. 次の段（調査で材料は揃っている）

1. **栄養ケア・マネジメントの記録と期限**: 1 回の実施（スクリーニング／アセスメント／モニタリング）= 1 レコード。期限は 低リスク 3 月毎・高リスク 2 週毎・中リスクは施設で決める値、再スクリーニング 3 月毎、入所後 1 週間以内。「今日」にやること として出す。前回複写とリスク別の定型文。様式 4-1-1 の形で印刷
2. **LIFE の CSV**: 仕様 v0310（122 項目、`eiyo-kanri_research\data\life\`）。項目の対応表を版つきの設定データにする。食事形態コード 50/40/30/22/21/10/02/01 は主食・副食マスタに列を足して対応
3. **禁食 × 献立の突き合わせ**: その日の食材（または「パンの日」「麺の日」）を入れると、当たる人と代わりの物が調理指示の備考として出る。献立を自前で持たない委託施設でも使える軽い形から
4. **補食・栄養補助食品のラベルと時刻別の配布表**
5. **入所時の聞き取り様式と、退所時の栄養情報提供書**
6. **複数のパソコンで使う**: 共有フォルダのデータファイルに保存する方式（ブラウザの保存領域は共有フォルダから開いても共有されない）
7. 体重の推移グラフ、Alb など他の測定値（`measures` は kind つきで足せる形にしてある）
8. 献立・成分表（既存 nutrition-app からの取り込み）
